# `/write` Command Lyricist Routing

- **Date**: 2026-05-22
- **Mode**: Team Mode - Decision Meeting
- **Roles**: Product Leader, Engineering Lead, AI Ops Expert, Marketing Director
- **Topic**: Should Wavvy connect a `/write` command to the new `wavvy-lyricist` skill and `lyrics-review` harness?

---

## Phase 1: Expert Analysis

### Product Leader

Using a Problem Space / Solution Space frame:

- Problem: invoking `wavvy-lyricist` directly is precise but not natural for repeated creative work.
- User need: when a lyricist is needed, the user wants to say "write this" with minimal ceremony.
- Product value: a `/write` alias lowers friction and makes the new lyricist feel like a usable tool, not just documentation.

Recommendation: connect `/write`, but keep it scoped to Wavvy lyric writing. The command should not become a generic "write anything" command.

### Engineering Lead

Using a Build for Today / Modular Design frame:

- Build only a thin router. Do not duplicate lyric rules in the command.
- The canonical logic should remain in `skills/wavvy-lyricist/SKILL.md`, `MASTER/lyrics/skills/WAVVY_LYRIC_SKILL_SPEC.md`, and `wavvy.py lyrics-skill`.
- The command should parse mode and target, then route to the skill and optionally run the harness.

Recommendation: implement as a command shim:

- Claude Code: `/write`
- Codex: `-write`
- Shared behavior: route to `wavvy-lyricist`.

### AI Ops Expert

Using an SSOT / trigger-surface frame:

- Codex policy uses hyphen triggers, not slash triggers. So `/write` is appropriate for Claude Code, while Codex should expose `-write`.
- Do not create a new public persona or a separate "writer agent" policy. This is a command alias over the existing skill.
- The command must preserve mode boundaries: `full-lyric-draft`, `suno-prompt-only`, `review-only`.

Recommendation: if implemented, register it as a Wavvy-local command and document the slash/hyphen distinction.

### Marketing Director

Using a messaging clarity frame:

- `/write` is better than `/wavvy-lyricist` for creative flow.
- It creates a simple mental model: "call the Wavvy writer."
- Risk: `/write` can sound broader than lyrics, including YouTube copy, concept text, changelog, or prompt engineering.

Recommendation: keep the command copy explicit: "Wavvy lyric write/rewrite/review." If non-lyric writing is requested, route elsewhere or ask one clarification.

## Phase 2: Synthesis

### Agreements

- Connecting a write command is useful.
- It should be a thin alias over `wavvy-lyricist`, not a second source of writing rules.
- It must support the three existing modes.
- Claude and Codex trigger formats should differ: `/write` for Claude, `-write` for Codex.

### Conflicts

- Product and Marketing prefer the shortest command name.
- Engineering and AI Ops worry that `/write` is too broad and can create routing ambiguity.

### Trade-off

| Option | Pros | Cons | Support |
|---|---|---|---|
| `/write` / `-write` | Lowest friction, memorable | Ambiguous if used for non-lyric writing | Product, Marketing |
| `/lyric` / `-lyric` | Clear scope | Less natural as a creative command | Engineering, AI Ops |
| No command | No new trigger surface | Skill remains harder to invoke | None |

### Recommendation

Use `/write` for Claude Code and `-write` for Codex, but define it as a Wavvy lyric-only router.

Minimum command behavior:

1. Read the target series concept and Wavvy lyric SSOT.
2. Load `skills/wavvy-lyricist/SKILL.md`.
3. Select or infer one mode: `full-lyric-draft`, `suno-prompt-only`, or `review-only`.
4. Produce the skill's required output sections.
5. When an artifact path exists, run `python3 wavvy.py lyrics-skill ... --artifact ... --mode ... --json`.
